## ADR-001：不用 tree-sitter，用 `es-module-lexer` + 正则规则表

**日期**：2026-09-02（开工前）

**选了**：JS/TS 用 `es-module-lexer` 提取 import；其他语言用「一条提取正则 + 一条路径映射规则」的规则表。

**放弃了**：`web-tree-sitter` 完整语法树解析。

**为什么**：画依赖图只需要 import 语句，不需要完整 AST。tree-sitter 每支持一种语言要加载一个 WASM 语法包并写一遍 query，边际成本是「几天」；规则表方案是「半小时」。对这个用途，完整 AST 是过度设计。

**代价**：正则方案在边缘语法上会漏（多行 import、条件导入、字符串拼接的动态 import）。接受，并在解析报告里如实展示失败样本。函数级钻取（V2）时再引入 tree-sitter。

## ADR-002：纯浏览器本地，无后端、无账号、无数据库

**日期**：2026-09-02（开工前）

**选了**：File System Access API 读本地目录，全部计算在浏览器（Worker）内完成。

**放弃了**：上传代码到服务端解析；用户账号与云端保存。

**为什么**：代码是敏感资产，「不上传」是硬需求而不是营销话术——用户可以打开 DevTools Network 面板自行验证，这种可验证性是服务端方案给不了的。附带收益：零服务器成本、零运维、零合规负担。

**代价**：无法跨设备同步、无法生成分享链接、受浏览器内存限制。V1 全部接受。

## ADR-003：做到符号级（L2），明确不做调用图（L3）

**日期**：2026-09-02（开工前，当天修订）

**背景**：初版决定「V1 只做文件级」。复审时认为纯文件级信息量不足，看不到模块内部，重新拆解了「函数级」这个说法。

它其实是三个层次，成本差数个量级：

| 层 | 节点 | 边 | 需要什么 | 成本 |
|---|---|---|---|---|
| L1 文件级 | 文件 | import 关系 | 路径解析 | 2 周 |
| L2 符号级 | 导出符号 | 谁用了谁的哪个符号 | 解析 import/export 名称 | +3~4 天 |
| L3 调用图 | 函数 | 调用关系 | AST + 作用域 + **类型推断** | 月级 |

**选了**：L1 + L2。

**放弃了**：L3。

**为什么做 L2**：`es-module-lexer` 本来就同时返回 imports 和 exports，做 L2 几乎不引入新依赖。它能把边从「A 依赖 B」细化成「A 用了 B 的 `format`」，钻取体验就有了；并且白送一个「疑似死代码检测」——无入边的导出符号即疑似未使用。这是个能单独拿出来讲的功能点。

**为什么不做 L3**：要解析 `obj.method()` 调的是哪个 `method`，必须先知道 `obj` 的类型。再叠加高阶函数、回调、动态派发、re-export 链——这等于写一个类型检查器。Sourcegraph 的 SCIP 和 GitHub 的 stack-graphs 都是多年工程，不是「多花几天」能覆盖的量级。

**代价**：
- 工期从 14 天增至 18 天。
- 看不到函数间调用关系，只能看到「文件 A 用了文件 B 的哪个导出」。
- 死代码检测会有误报（动态引用、外部消费方、库的公开 API），因此界面上必须标注为**「疑似」**——把猜测说成结论是产品诚信问题。

## ADR-004：修正 ADR-003 的措辞——L3 并非「做不到」，而是「不划算」

**日期**：2026-09-02

**背景**：ADR-003 写的是 L3 调用图「月级、大概率做不完」。调研 CodeGraph 后发现这话说满了——它确实做了 callers/callees、循环依赖、blast radius。

**修正**：L3 有两条路线，成本不同。

| 路线 | 做法 | 准确率 | 成本 |
|---|---|---|---|
| **L3-lite** | tree-sitter 语法层提取调用点 + **按名字匹配**到定义 | 对 `obj.method()`、重载、动态派发会误判 | 可行 |
| **L3-full** | 类型推断解析（SCIP / stack-graphs 那种） | 高 | 月级，判断依然成立 |

CodeGraph 走的是 L3-lite。

**决定**：V1 仍不做 L3，但理由改为——**L3-lite 要重新引入 tree-sitter 和逐语言 query，正是 ADR-001 刻意避开的成本，且准确率存疑**。这是一个有意识的取舍，不是能力边界。

**为什么记这条**：原判断说满了，这个修正过程本身要留痕。「我最初判断错了，调研后修正如下」比一份全是正确决策的文档可信得多。

## ADR-005：借鉴 CodeGraph 的需求清单，不借代码

**日期**：2026-09-02

**背景**：`codegraph-ai` 暴露 42 个 MCP 工具，每个工具 = 一个真实存在的「人想问代码库的问题」。这相当于一份现成的需求调研。

**选了**：借**需求**和**工程做法**，代码自己写。

从他们的工具清单映射出的 V1 新增功能：

| 他们的工具 | 我们的做法 | 为什么图比文字强 |
|---|---|---|
| `find_hot_paths` | 节点大小 = **传递入度**（原设计是 LOC） | 被依赖得多才是枢纽；LOC 大只说明文件长 |
| `find_circular_deps` | 图上高亮环 | 文字列表根本看不清环的形状 |
| `find_entry_points` | 作为「从这里开始看」的导航起点 | 解决打开大图不知从何看起 |
| `analyze_impact` | 点击节点高亮传递影响范围 | blast radius 用高亮表达远胜读列表 |

另外借鉴两个工程做法：
- **公布真实基准**：他们写「Swift 编译器 27k 文件索引 ~100 秒」。README 里放同样形式的表——数字比形容词有说服力，面试时能直接甩出来。
- **增量 reconciliation**：`(size, mtime)` + 内容哈希对比工作区。放 V2。

**放弃了**：复用他们的代码。两个项目分别是 MIT 和 Apache-2.0，法律上完全允许——**但自己写才有面试价值**，这是本项目的首要目的。

**代价**：工期 18 → 20 天。这是有意识的范围增加，理由是这四条全部只在已有图数据上做文章，不引新依赖、不引新解析，杠杆比极高——**它们把「一张好看的图」变成「一个能回答问题的工具」**。增量索引那条已明确推到 V2，没有一起加。

**一个反面确认**：调研中没有发现任何一个提供「给人看的、可分享的交互式全景图」的同类工具。定位空白成立。

## ADR-006：Day 1 验证结果——绿灯，但指标有盲区

**日期**：2026-09-02

**做法**：`scripts/verify-resolver.mjs`，在 5 个本地真实项目上跑路径解析。

### 结果

| 项目 | 代码文件 | 耗时 | 内部 import | 命中率 |
|---|---|---|---|---|
| my_site (Astro) | 16 | 15ms | 11 | 100% |
| mini_toy | 56 | 278ms | 121 | 100% |
| travel_map/web | 76 | 29ms | 164 | 100% |
| resume-site | 13 | 4ms | 19 | 100% |
| conquest | 39 | 36ms | 0 | 样本无效（无内部 import） |

**判定：绿灯（≥90%），按原计划推进。** 但下面三条附注同等重要。

### 发现 1：脚本本身有两个 bug，改完命中率才到 100%

- **漏扫 `.astro`/`.vue`/`.svelte`** —— 初版 my_site 只扫到 8 个文件，「命中率 0%」其实是「根本没测到」。
- **缺 `.js` → `.ts` 映射** —— ESM + TypeScript 的标准约定是 import 写 `'./x.js'`、磁盘上是 `'./x.ts'`（Node ESM 要求写扩展名，tsc 不重写它）。不处理这条，所有遵循该约定的项目都会大面积误判。这是唯一一个真实失败样本教会我们的。
- **`0/0` 被判成 ❌** —— conquest 没有任何内部 import，除法产生 0.0%，被误报成红灯。

> **Day 1 的价值不在那个 100%，在这三个 bug。** 如果直接进入开发，它们会一路潜伏到 UI 阶段才暴露。

### 发现 2：es-module-lexer 失败在 JSX，不在 TS

实测各语法：TS 类型注解、`import type`、泛型箭头、interface、enum、`as satisfies`、装饰器**全部通过**；**只有 JSX/TSX 解析失败**。

这解释了 35%–77% 的正则回退率——React 项目里大部分文件是 TSX。

**结论：ADR-001 的措辞要修正。** 不是「用 es-module-lexer，正则做兜底」，实际是**「正则承担主要工作，lexer 处理纯 TS/JS 文件」**。当前混合方案已达 100% 命中率，V1 保持不变；若后续需要更高精度，候选是 `oxc-parser`（Rust/WASM）。

### 发现 3：命中率这个指标有盲区 ★

**它衡量的是「找到的 import 里有多少解析成功」，不衡量「有没有漏掉 import」。**

正则回退可能漏掉多行 import、被注释或字符串里的伪 import 干扰——**这类假阴性在当前指标里完全不可见**。100% 不代表图是完整的。

**对策**：Day 2 补一个反向校验——用一个独立方法（如 `oxc-parser` 或 `tsc --listFiles`）统计 import 总数，和当前提取器对账。差值就是漏掉的量。

### 发现 4：样本规模不足

最大项目仅 76 个文件，验收标准写的是 2000 个文件 / <10 秒。**当前数据只能说「没发现红灯」，不足以支撑性能和规模结论。** 需要在一个大型开源项目上复跑。

## ADR-007：规模验证通过——解决 ADR-006 的「发现 4」

**日期**：2026-09-02

**做法**：在三个大型开源仓库上复跑（浅克隆），覆盖不同风格：TSX 重度（excalidraw）、纯 TS monorepo（vite）、多框架 monorepo（TanStack/query）。

### 结果（修复 `.d.ts` 缺陷后）

| 项目 | 代码文件 | 解析耗时 | import 总数 | 内部 import | 命中率 |
|---|---|---|---|---|---|
| excalidraw | 668 | 306ms | 4450 | 3941 | **99.9%** |
| vite | 1598 | 546ms | 3776 | 2044 | **99.3%** |
| TanStack/query | 1230 | 407ms | 4146 | 1614 | **99.4%** |
| **合计** | **3496** | — | **12372** | **7599** | **99.6%** |

> 这张表直接进 README（ADR-005 借鉴的做法）。

### 又一个真实缺陷：`.d.ts`

54 个失败样本里有一半指向纯类型模块——`hmrPayload.d.ts`、`anymatch.d.ts`、`types.d.ts`。原候选列表没有 `.d.ts`，`JS_TO_TS` 映射也没有 `.js → .d.ts`。

补上后失败数 **54 → 27**，三个仓库命中率全部提升。**又一个只有真实大仓库能逼出来的 bug**——前五个小项目一个都没暴露它。

### 剩余 27 个失败，全部是设计上无法解析的

分类核对后确认没有真正的解析器缺陷：

| 类别 | 例子 | 判断 |
|---|---|---|
| 构建产物引用 | `./dist/node/cli.js` | 合理——`npm run build` 后才存在 |
| **测试用的故意坏引用** | `has-invalid-import.js → './non-existent.js'` | **解析失败才是正确行为** |
| 框架生成的虚拟模块 | SvelteKit 的 `./$types` | 不在磁盘上 |
| monorepo 里的绝对路径 | `/index.html?raw` | project root ≠ repo root，已知限制 |
| 别名子路径 | `@excalidraw/excalidraw/element/types` | 别名指向 `index.tsx`，子路径无法展开 |

**在解析报告里应把前三类单独归一栏，不计入失败**——否则会误导用户以为工具有问题。

### 性能

vite 1598 文件 / 546ms。外推 2000 文件约 700ms，**验收标准是 <10 秒，余量 14 倍**。

**但这是 Node + 热文件缓存的数字，不是浏览器 File System Access API 的数字。** 浏览器逐文件走权限化的异步 API，会显著更慢。**性能验收必须在真实浏览器环境重测**，当前数字只能证明「算法本身不是瓶颈」。

## ADR-008：core 层不依赖任何运行环境 API

**日期**：2026-09-02（Day 2）

**选了**：`src/core` 全部是纯函数，不 import `node:*`，也不碰 DOM。

- 自己写了最小 posix 路径工具 `src/core/path.ts`，替代 `node:path`
- 文件是否存在由调用方通过 `ResolveContext.has` 注入，core 不做任何 I/O
- 读文件、遍历目录由适配层负责：Node 用 `fs`，浏览器用 File System Access API

**放弃了**：直接用 `node:path`，靠打包器 polyfill 到浏览器。

**为什么**：
1. 同一份解析逻辑要在两个环境跑——验证脚本（Node）和产品（浏览器）。**逻辑复制两份必然发散**。
2. 纯函数天然可单测，不用 mock 文件系统。43 个单测全部是零 I/O 的。
3. 打包器 polyfill 的 `path` 在边缘行为上（尤其 Windows 盘符）和 Node 不一致，是隐蔽 bug 的温床。

**代价**：`path.ts` 要自己实现并自己保证正确性，特别是 `extname` 必须识别 `.d.ts` 这类双扩展名——这正是 ADR-007 那个缺陷的根因。

## ADR-009：Day 2 单测抓到两个「指标看不见」的 bug

**日期**：2026-09-02（Day 2）

写完 43 个单测后跑出两个失败。**两个都是真 bug，不是测试写错。**

### Bug 1：虚拟模块判定抢在别名匹配之前

`/^~/` 被列进虚拟模块模式，但 `~/*` 是 Nuxt 等项目**极常见的 tsconfig 别名**。结果所有 `~/...` 的合法别名被判成「框架虚拟模块」，静默丢边。

**修复**：别名匹配移到最前——别名可能长得像虚拟模块（`~/*`），也可能长得像裸包（`@scope/x`），必须最先尝试。同时从模式表里删掉 `^~`，无别名的 `~foo` 会自然落入 external。

### Bug 2：正则贪婪可选组跨行吞掉整条 import ★

原模式 `(?:[\s\S]*?\sfrom\s*)?` 的可选组是**贪婪**的，且 `[\s\S]` 能跨行。遇到无绑定导入时：

```js
import './side-effect'      // ← 被整条吞掉
export { x } from './b'     // ← 可选组一路扫到这里的 from
```

匹配区间从上一行的 `import` 一直延伸到下一行的 `'./b'`，`'./side-effect'` 直接消失。

**修复**：子句改用 `[^'"]*?`（无法跨越引号，也就无法跳到下一条语句），可选组改为惰性 `??`。代码里留了「禁止改回 `[\s\S]`」的注释。

### 为什么这两个值得单独记一条

**它们在 Day 1 的命中率指标里完全不可见。**

命中率 = 成功解析 / (成功解析 + 失败)。被静默漏掉的 import **根本不进入分母**——漏得越多，命中率反而越好看。这正是 ADR-006「发现 3」预警的假阴性盲区，而堵住它的不是更多真实仓库，是单测。

**证据**：修复后在同样三个仓库上复跑，提取到的 import 总数增加 64 条（excalidraw +54、query +8、vite +2），命中率同步上升：

| 项目 | 修复前 | 修复后 |
|---|---|---|
| excalidraw | 99.9% | 99.9% |
| vite | 99.3% | **99.7%** |
| TanStack/query | 99.4% | **99.8%** |

那 64 条边，在写单测之前是不存在于图里的，而且没有任何指标会告诉我们。

## ADR-010：分析流水线也提到 core，Node 与浏览器共用

**日期**：2026-09-02（Day 3）

**选了**：把「读文件 → 提取 → 解析 → 建图」整条流水线放进 `src/core/analyze.ts`。文件内容通过 `SourceFile.read()` 注入，适配层只负责「怎么拿到文件」：

- `scripts/verify-resolver.ts` → `node:fs`
- `src/adapters/browser.ts` → File System Access API

**放弃了**：让两边各写各的分析循环。

**为什么**：Day 3 要回答的问题是「浏览器比 Node 慢多少」。**如果两边的流水线不是同一份代码，这个对比就没有意义**——差异可能来自实现不同而非环境不同。共用之后，唯一的变量就是取文件的方式。

**顺带的收益**：并发池（`mapPooled`）也只写一份。Node 侧实测读文件累计 9404ms，被 32 并发压到墙钟 300ms——并发参数对两个环境都是同一个旋钮，可以直接对比调优效果。

### Node 侧基线（同一条流水线，并发 32）

| 项目 | 代码文件 | 目录遍历 | 分析墙钟 | 合计 | 读文件累计 | 命中率 |
|---|---|---|---|---|---|---|
| vite | 1598 | 90ms | 300ms | **390ms** | 9404ms | 99.7% |

**浏览器侧数字待测**——`showDirectoryPicker()` 弹的是操作系统原生对话框，自动化无法驱动，必须人工执行。这是 ADR-007 遗留的最后一个未验证风险。

### 并发池的必要性

浏览器端一次性对上千个文件发起 `getFile()` 会把主线程拖死。`mapPooled` 用固定数量的 worker 轮询游标，而不是 `Promise.all` 全量展开。UI 上把并发数做成了可调选项，正是为了实测这个旋钮的影响——**先测量再决定要不要上 Web Worker，而不是照着计划书里的假设直接上**。

## ADR-011：分类色只用 3 个槽位，其余折叠为 Other

**日期**：2026-09-02（Day 6–8）

**背景**：按顶层目录给节点着色。直觉做法是「有几个目录就用几种颜色」，一个仓库通常有 6–10 个顶层目录。

**选了**：**只给节点数最多的 3 个目录分配具名颜色，其余全部折叠成一个中性灰 Other。**

**为什么**：力导向图是 **all-pairs 形态**——布局是自由的，任意两种颜色都可能挨在一起。这和柱状图/堆叠图不同，后者只有*相邻*槽位需要互相区分。

在 all-pairs 约束下，8 色分类板无法同时满足色觉缺陷分离下限；**前 3 个槽位是能全部通过的最大集合**。第 4 个槽位会把黄和橙同时放上屏幕，这一对在 all-pairs 下同时跌破常视和色觉两条下限。

**验证方式**：跑了调色板验证器，没有靠肉眼判断。深色表面 `#1a1a19`，`--pairs all --mode dark`：

```
[PASS] 亮度带      3 个全部落在 L 0.48–0.67
[PASS] 彩度下限    3 个全部 ≥ 0.1
[PASS] 色觉分离    最差 all-pairs ΔE 9.4 (deutan)
[PASS] 常视分离    最差 all-pairs ΔE 20.9
[PASS] 表面对比度  3 个全部 ≥ 3:1
```

**其他编码决策**：
- **节点大小 = 传递入度**，半径开方（面积正比于数值，否则枢纽节点吃掉整个画面）。不用 LOC——文件长不等于重要。
- **循环依赖用红色描边而非填充色**：状态色永远不单独承载语义，描边是二级编码，图例里也有对应条目。
- **只给传递入度 ≥12 的节点直接标注文件名**，且仅在放大后显示。每个点都挂字等于没有标注。
- **图之外必须有等价的表格视图**（枢纽 / 入口点 / 循环 / 孤岛四张表）——身份不能只靠颜色传达。

**代价**：目录多的仓库里，第 4 个以后的目录在颜色上不可区分，只能靠 hover 和表格辨认。这是 all-pairs 形态的硬约束，不是可以靠"再加一种颜色"绕过的问题。

## ADR-012：命中率盲区的第三次发作——tsconfig 只在根目录找 ★

**日期**：2026-09-02（Day 8）

**怎么发现的**：**看截图看出来的，不是测出来的。**

第一次在浏览器里跑真实项目，图上 76 个节点只有 9 条边、65 个孤岛，而 `main.tsx` 和 `App.tsx` 双双被判成孤岛——`main.tsx` 不可能不 import `App.tsx`。

**根因**：适配层只在用户选中的根目录找 `tsconfig.json`。用户选的是 `travel_map/`（父目录），而 tsconfig 在 `travel_map/web/` 下。别名一条都没加载，于是所有 `@/components/x` 匹配不到别名，落入「裸 specifier → 外部包」分支。

Node 侧完整复现：243 个 import 里 **234 个被归类成外部包**，只剩 9 条边。

### 为什么这条要标星

**命中率显示 100%。**

命中率 = 成功解析 / (成功解析 + unresolved)。被误判成 external 的 import **根本不进分母**——234 个导入静默消失，指标反而是满分。

这是 ADR-006「发现 3」那个盲区的第三次发作，而且一次比一次隐蔽：

| # | 形态 | 谁抓到的 |
|---|---|---|
| 1 | 正则贪婪组跨行吞掉整条 import | 单测（ADR-009） |
| 2 | `~/*` 别名被误判成虚拟模块 | 单测（ADR-009） |
| 3 | **整个仓库的别名没加载，import 全归类成 external** | **肉眼看图** |

**教训：单测和聚合指标都抓不到「大面积误分类」。** 只有把产物画出来看，才能发现「这图不对劲」。这是把可视化提前到 Day 8 的意外收益——如果按原计划先把 L2 做完再画图，这个 bug 会潜伏到第 15 天。

### 修复一：多份 tsconfig + 最近祖先匹配

适配层收集**整棵树**的 `tsconfig.json` / `jsconfig.json`，`analyze` 为每个文件挑选最近祖先的作用域——这是 TypeScript 的真实行为。作用域按目录深度降序排列，第一个命中的即最近。

结果：**9 条边 → 164 条边**，与直接扫 `web/` 子目录的结果完全一致。

### 修复二：让这类失败以后能被指标看见

新增 `externalAliasLike` 指标：统计**长得像别名却没匹配上**的裸 specifier。

判据是 `^(@\/|~\/|#)`。关键在于 `@/` 和 `@scope/pkg` 可以严格区分——npm 作用域包必须是 `@scope/name` 的形式，`@` 后面直接跟斜杠的不可能是包名。所以这个检测**不会误报真实的 npm 包**。

`externalAliasLike > 0` 时界面直接告警「图可能缺边」。修复前该指标是 155，修复后是 0。

**这条修复比第一条更重要**——第一条修了一个 bug，第二条让整个这一类 bug 从此可见。

**代价**：`ResolveResult` 的 external 分支多了一个字段，6 个旧测试的 `toEqual` 断言要改成 `toMatchObject`。

## ADR-013：边的语义是「依赖关系」，不是「import 语句」

**日期**：2026-09-02（Day 8）

**怎么发现的**：截图上图例写「153 边」，而解析报告写「164 依赖边」。**同一个东西在两处显示两个数字，没有任何解释——这本身就是产品缺陷。**

**两处差异各有来源，都需要修**：

1. **11 条边指向非代码文件**。`import './App.css'` 解析到了真实存在的文件，被计为 `resolved` 并产出一条边；但 `.css` 不在代码文件集合里，图上没有对应节点，`buildGraph` 只好把边丢掉——产生了悬空边。
   **修复**：解析成功但目标非代码文件时归为 `asset`，不产出边。

2. **同一文件对同一目标的重复导入**（`import type { T } from './b'` 与 `import { v } from './b'` 并存）产生两条边，建图时被合并成一条。
   **修复**：在 `analyze` 内按 `(source, target)` 去重。

**定下的语义**：
- **边 = 一个依赖关系**（去重后）
- **`stats.resolved` = 一次成功解析**（不去重，衡量解析器表现）

两者本就该不同，但必须各自说得清、且在任何地方显示的边数都一致。修复后处处都是 153。

**代价**：丢失了重复导入中第二条的 `raw` 字符串。可接受——它和第一条指向同一个文件。

## ADR-014：目录树的构建与展平做成纯函数

**日期**：2026-09-02（Day 9–10）

**选了**：`src/core/tree.ts` 承担建树、可见行展平、过滤、祖先计算、默认展开策略；`ui/FileTree.tsx` 只负责渲染和滚动。虚拟化用 `@tanstack/react-virtual`。

**放弃了**：直接用 `react-arborist`（原计划）。

## ADR-015：L2 符号级连边与疑似死代码

**日期**：2026-09-02（Day 12–15）

### 提取层：记录源名，不是本地名

`import { format as fmt }` 记的是 **`format`**（导出方的名字），不是 `fmt`。符号边要连到目标文件的导出上，本地别名对目标毫无意义。这一步在 `parseImportClause` 里做，纯函数，13 个单测覆盖各种写法（默认、具名、混合、`import type`、内联 `type`、多行、re-export）。

顺带抓到一个 bug：`import App, * as ns from './x'` 原本没被识别成命名空间——因为无花括号分支直接返回了「默认导入」，没检查 `*`。

### 三条豁免规则，缺一条就大面积误报

| 规则 | 为什么必须有 | excalidraw 实测豁免数 |
|---|---|---|
| 有入边 | 显然 | 1405 |
| **命名空间导入的文件，全部导出豁免** | `import * as ns` / `export * from` / 动态 import 无法确定用了哪几个符号 | **598** |
| 入口点文件的导出单独归类 | 没人依赖入口点，它的导出自然没有仓库内引用 | 3 |

**第二条是命门。** excalidraw 里 598 个符号靠它豁免——不加这条，误报率会从 7% 飙到 35%，整个功能直接不可信。

### 实测结果

| 项目 | 导出符号 | 符号引用 | 疑似死代码 |
|---|---|---|---|
| travel_map | 131 | 326 | 12 |
| excalidraw | 2157 | 7539 | 151（7%） |

7% 是个可信的量级——既不是零（那说明检测没生效），也不是三分之一（那说明规则漏了豁免）。

### 「疑似」是硬约束

界面上必须写「疑似死代码」，且必须列出豁免统计和三条可能的误报原因（动态引用、仓库外消费方、库的公开 API）。

**把猜测说成结论是产品诚信问题**——这条写进了验收标准，不是可选的措辞偏好。而且它是加分项：说明作者知道自己方案的边界在哪。

### 顺带的语义变化

提取器现在按 specifier 合并同一文件的多条 import 语句，所以「一次解析」的单位从「import 语句条数」变成 **(文件, specifier) 对**。符号级引用不受影响——`import type { T }` 和 `import { v }` 来自同一 specifier，但两个符号都会各自连边，否则 `T` 会被误判成死代码。

## ADR-016：UI 按「区域」建立统一词汇表

**日期**：2026-09-02

**触发**：准备开始视觉与交互打磨。打磨阶段的每一次改动都以「改哪块」开头，

## ADR-017：界面改版——图幅（plate）作为视觉概念

**日期**：2026-09-02

**要求**：简约高级、少文案、卡片收进统一入口、主视图以侧栏和画布为主、画布加小地图。

**选了**：把界面做成**一张地图图幅**。不是装饰性比喻——制图学的部件和这个工具需要的东西一一对应：

| 制图学 | 这里 |
|---|---|
| 图幅内框线（neatline） | 画布与页面的分界 |
| 位置索引图（locator inset） | 小地图：全图缩略 + 视口矩形，点击跳转 |
| 图例（legend） | 目录配色 + 循环依赖 |
| 索引（index） | 侧栏文件清单 |
| 图幅注记 | 收进抽屉的分析表格 |

产品叫 Atlas，这套词汇是现成的，且**每个部件都对应一个真实功能**，不是套皮。

### 四处结构改动

1. **整屏三段栅格，主视图不产生页面滚动。** 之前是文档式的长页面，侧栏和画布只占上半屏。现在 `顶栏 / 工作区 / 详情栏`，工作区吃掉全部剩余高度。
2. **五张卡片 + 报告页 → 一个右滑抽屉。** 标签栏因此可以删掉。
3. **详情区从整卡压成单行。** 路径 + 三个数字，导出符号明细挪进抽屉。
4. **小地图**：读取力导向布局的实时坐标算包围盒，用 `screen2GraphCoords` 反算视口矩形，隔帧重绘（避免与主图争绘制预算）。

### 三条视觉纪律

- **强调色只用于「当前选中/聚焦」。** 之前蓝色同时是按钮、标签、选中、影响范围、节点色槽 1、进度条——"到处都是同一个亮色"是廉价感的主要来源。现在按钮和导航一律墨色 + 细线。
- **删掉全大写小标签。** 原 `.card-title` 是 uppercase + letter-spacing，这是典型的模板腔。
- **删掉中点连接的元信息串**（`A · B · C`），改成分隔的字段。

### 文案削减

删：页头副标题段落、画布底部的编码说明、详情区的整段解释。
留：**死代码的「疑似」声明**——它是准确性义务，不是可删的修饰（验收标准里写死了），只是从主视图移进了数据所在的位置。

### 一条不能动的约束

`--stage` 必须保持 `#1a1a19`。分类色是针对这个表面色验证过的（ADR-011）。页面底色改成更暗的 `#0d0d0d` 让图幅浮起来——**只动周围，不动画布本身**，验证结论才继续有效。改版后重跑了一次验证器确认。

**代价**：`InspectorPanel` / `InsightsGrid` / `ReportView` / `primitives` 四个文件被 `NotesDrawer` + `DetailRail` 取代。115 个单测和生产构建均通过，核心逻辑零改动。

## ADR-018：圆角面板与可拖拽侧栏

**日期**：2026-09-02

**要求**：侧栏支持拖宽、整体改成圆角卡片形式。

### 圆角卡片，但要分级

"所有东西同一个圆角、每张卡一层同样的灰色投影"是最容易滑向模板感的做法。
所以圆角按层级分四档，而不是一个值贯穿全场：

| 令牌 | 值 | 用在 |
|---|---|---|
| `--r-panel` | 14px | 侧栏、画布、详情栏、抽屉 |
| `--r-card` | 10px | 抽屉内部的内容卡片 |
| `--r-control` | 8px | 按钮、输入、下拉、小地图 |
| `--r-row` | 6px | 侧栏行、表格悬停行 |

配套四层底色：`--plane` < `--board` < `--panel` < `--panel-2`。
**阴影只给真正浮起来的东西**（分析抽屉），面板之间靠 1px 边框和底色差区分。

顺带删掉了单独画的 neatline 图层——面板自己的圆角边框就是图幅内框线，
留着两层边是多余的（"出门前照镜子，摘掉一件"）。

### 可拖拽侧栏

用 **Pointer Capture** 而不是在 `window` 上挂 `mousemove`：拖到浏览器窗口外再松手也不会丢事件，
也不需要手动清理监听。

- 键盘可达：分隔条是 `role="separator"`，`←/→` 调 16px，`Shift` 加速到 48px，`Home` 复位
- 双击复位，宽度存 `localStorage`，范围 190–560px
- 分隔条默认隐形，悬停/聚焦/拖动时才显示一条 2px 线——静止时不该有多余的视觉噪音

画布已经用 `ResizeObserver` 监听尺寸，拖动时力导向图自动跟着重排，不需要额外处理。

### 两个 grid 陷阱，第二个把界面整个搞塌了

**其一**：警告条原本是 `.app` 的直接子元素。`.app` 用 `grid-template-rows` 只声明了两行，
多出来的子元素会被追加到**后面**的隐式行——警告条跑到工作区下面去了。
改成收进 `.board` 里的单一 `.banners` 容器。

**其二**：给空的 `.banners` 加了 `:empty { display: none }`。
`display: none` 会把元素**从 grid 流里彻底移除**，于是后面的行整体上移：
工作区拿到了第一行的 `auto`（缩到内容高度，只剩 90px），详情栏拿到了 `minmax(0,1fr)`（撑满整屏）。
界面完全塌掉。

**根治办法不是删掉那条规则，而是给三行显式指定 `grid-row`。**
靠子元素书写顺序隐式分配行号，只要任何一个子元素条件性消失就会连锁移位；
显式指定之后，这类改动不再有副作用。空的 flex 容器本身高度就是 0，不需要 `display: none`。

**代价**：CSS 从 5.5 KB 涨到 9.9 KB（gzip 2.7 KB）。115 个测试与生产构建均通过，逻辑零改动。

## ADR-019：传递入度在大仓库里会饱和——节点大小改用直接入度 ★

**日期**：2026-09-02

**怎么发现的**：又是看截图。在 excalidraw（668 文件 / 3327 边）上，图糊成一团毛球。

**根因不在布局，在度量。** 侧栏的数字直接暴露了问题：

```
errors.ts   510      history.ts  509      i18n.ts     509
gesture.ts  509      snapping.ts 509      types.ts    509
```

**668 个文件里几乎每个的传递入度都是 509 上下。** 强连通的仓库里，
「有多少文件直接或间接依赖我」这个量会饱和——几乎所有节点都能被几乎所有节点到达。

两个后果同时发生：
1. **失去区分度**：509 和 510 之间的差别是噪音，侧栏那一列数字等于没有信息。
2. **节点巨大**：`1 + √509 ≈ 23.6`，再乘 1.5 得到 **35px 半径**。668 个这么大的圆必然重叠。

这推翻了 ADR-005 里「节点大小用传递入度」那条——**它在小仓库上是对的，在大仓库上失效**。

### 修正

**节点大小改用直接入度，并把半径映射到固定像素区间：**

```
r = 2.5 + 8.5 × √(direct / maxDirect)      → 恒定落在 [2.5, 11]px
```

- 直接入度**不饱和**，而且「多少人直接 import 我」本来就是「枢纽」的字面含义
- 按当前仓库的最大值归一化，**无论仓库多大，画面密度都可控**
- 传递入度保留在提示框和影响范围里——「改这个会波及 509 个文件」在那里才是有用信息

侧栏数字同步改成直接入度。

### 另外三处「挤」的来源

1. **d3-force 默认不含碰撞力**，节点会直接叠在一起。加了 `forceCollide(r + 1.5)`，两次迭代。
2. **斥力和连线长度没有随规模调整**。改成按节点数缩放：`charge = -38 - min(170, n/3)`，密集图连线长度 36。
3. **循环依赖占比过高时红圈变成纯噪音**。excalidraw 有 346/668 个节点在环里——给一半以上的节点画圈等于没标注。占比超过 25% 时默认关闭该图层，用户想看再打开。

密集图（>220 节点）另外压低连线不透明度、去掉箭头、把标签门槛从直接入度 4 提到 14。

### 教训

**同一个指标在不同规模下的表现可能完全相反。** 76 个文件的项目上传递入度工作良好，
668 个文件上就废了。所以「在真实的大仓库上看一眼产物」是不能省的步骤——
单测和聚合指标都不会告诉你「这张图糊了」。这已经是第二次靠肉眼截图发现关键问题（第一次见 ADR-012）。

## ADR-020：影响范围必须分层，默认 2 跳 ★

**日期**：2026-09-03

**选了**：`impactOf(g, node, maxDepth)` 一次 BFS 算出**全部**跳数，层级上限只做筛选。
画布工具条给 `1 跳 / 2 跳 / 3 跳 / 全部` 四档，默认 2 跳。

**放弃了**：原来的无限反向可达（`Set<string>`，不带跳数）。

### 症状

用户的原话：「聚焦节点会把间接依赖也链接起来，这个间接有层级限制吗？现在以 excalidraw 为例，
很多节点中时都会出现 500 多链接节点。」

没有限制。`impactOf` 是无限反向 BFS，谁能沿反向边走到就算谁。

### 为什么

**这是 ADR-019 的同一个病根，第二次发作。** 019 是传递入度作为**视觉编码**饱和，
这次是同一个传递闭包作为**交互反馈**饱和：excalidraw 的 668 个文件里有一个 346 节点的
强连通分量，只要选中的文件沾上这个分量，反向可达立刻涨到 509——**点哪儿都亮同一片**，
等于没有反馈。当时 019 只改了节点半径，把「影响范围」这条路径漏掉了。

跳数是有区分度的量，而且每一档都对应一个真实的问题：

| 档位 | 回答的问题 |
|---|---|
| 1 跳 | 谁**直接** import 我 |
| 2 跳 | 改坏了谁会先炸 |
| 3 跳 | 波及面的大致形状 |
| 全部 | 只适合看总量 |

默认 2 跳而非 1 跳：1 跳看不出链路形状，2 跳能看到扇出又不至于饱和。

### 连带修掉的：边高亮

原来的规则是「两端都在聚焦集里就点亮」。在强连通分量里这意味着同层之间的**横向边**
也全部点亮——那团糊住的线有一半是它贡献的。改成只点亮**传播步**：
边的方向是 source import target，影响沿反向传播，所以

```
一条边参与传播 ⟺ 跳数(source) === 跳数(target) + 1
```

结果是从选中节点向外的一棵扇形树，而不是一团网。

### 代价与防瞒报

限了层级就有了「没说出来的部分」。所以 `Impact` 里**同时**带 `reached`（当前层级内）
和 `total`（不限层级）与 `farthest`（最远跳数），详情栏显示成 `12 个文件受影响 / 全部 509`。
一次 BFS 就把全部跳数算完了，`total` 是白送的——**没有任何理由为了省事而只报一个数**。
这条和「疑似死代码」里「疑似」两个字不可省略是同一条原则：不能把筛选后的结果说成全部。

复杂度不变，仍是一次 BFS。

### 教训

**推翻一个指标的时候，要把它的所有使用点一起过一遍。** ADR-019 已经写明了传递闭包会饱和，
但只改了用到它的一处（节点半径），另一处（影响范围高亮）原样留着，两周后由用户当面指出。
写 ADR 的时候如果顺手 grep 一遍这个概念的全部引用，这条本来不用存在。

## ADR-021：把饱和指标从展示里清干净 ★

**日期**：2026-09-03

**触发**：用户看着悬停提示框里的 `312 个文件直接引用 · 含间接 509 · 18 行 · 在循环中`
问：「那这里的详情卡有些数值是不是要变化一下？」

对。ADR-020 刚说完传递闭包在这个仓库里饱和，提示框里还挂着那个 509。
**这是 ADR-020 教训的即时复现**——我上一条刚写完「推翻一个指标要把所有使用点一起过一遍」，
自己就漏了两处。这次 `grep transitive` 找全了。

### 三处修改

**1. 悬停提示框：`含间接 N` → `引用了 N 个`（出度）**

一个几乎恒定的数字既没有信息量，又和详情栏里分层后的影响范围互相打架
（同一屏上「含间接 509」和「12 个受影响 / 全部 509」在说同一件事的两个版本）。
入度配出度才是这个圆的**局部形状**：谁用我、我用谁，两个都不饱和。

**2. 悬停提示框新增一行：与选中项的关系**

```
距 index.ts 2 跳
距 index.ts 5 跳（超出当前 2 跳，已淡出）
不受 index.ts 影响
```

画面上的明暗差别本身不解释自己。加了这一行，层级到底怎么算的就不用猜了——
这恰好也是用户最初提问的那个疑惑。

**3. 枢纽榜的排序键：传递入度 → 直接入度**

这条是三处里最严重的：原来按传递入度降序取前 40，
而 excalidraw 上前几十名全是并列 509，等于**在并列第一里随机取 40 个**，
「被依赖最多的文件」这个标题是假的。改按直接入度排，加 `localeCompare` 兜底保证稳定。

传递入度**作为一列保留**。并排放着能一眼看出它饱和了（一整列 509 本身就是信息），
当排序键才有害。

### 判据

一个指标能不能出现在界面上，取决于它在**当前这个仓库**里还有没有区分度。
传递入度在 76 个文件的项目上是好指标，在 668 个文件、含 346 节点强连通分量的项目上是常数。
所以规则不是「删掉它」，而是：

- **不做排序键**（并列会让排序变成随机）
- **不做视觉编码**（见 ADR-019）
- **不单独出现**（旁边必须有不饱和的数字作参照，否则读者无从判断它饱和了）

### 代价

提示框里少了一个数字，小仓库上那个数字本来是有用的。接受——
为小仓库保留一个在大仓库上会误导的展示，是拿正确性换信息量，方向反了。

## ADR-022：内置示例 = Code Atlas 分析它自己

**日期**：2026-09-03

**选了**：把本仓库的源码用 `import.meta.glob` 惰性打包进产物，
点「看示例」时走**真实流水线**当场分析。

**放弃了**：打包时预先算好一份 `result.json`；或者内置某个知名开源仓库的源码。

### 为什么需要它

部署出去之后有一个致命缺口：**打开链接的人本地并没有代码仓库。**
一个只会弹目录选择框的页面演示不了任何东西。
Chrome 以外的浏览器更是连按钮都是灰的，第一屏就只剩一句「不支持」。

### 为什么不用预算好的 JSON

演示一个分析工具，却给它喂预先算好的结果，等于什么都没演示——
观众没法区分「这个工具能分析代码」和「这个页面能画一张写死的图」。
现在屏幕上的每条边都是当场 extract + resolve 出来的，
所以它同时也是一次公开的正确性演示。

### 为什么是自己的源码而不是知名仓库

- 体积：本仓库源码约 130 KB，惰性分块后只有点了示例才下载；塞一个真实开源仓库要几 MB
- 许可与署名：不用处理别人的 LICENSE
- 自指本身是个好卖点：「这个工具正在分析它自己」

代价是图比较小（31 个文件），演示不了大仓库上的循环依赖和枢纽分布。
接受——大仓库的数字放在 README 的实测表里，那里更适合。

### 硬约束：示例必须走同一条路径

`scanDemo()` 返回的是和 `scanDirectory()` **形状完全一致**的 `BrowserScan`，
下游的 `analyze` / `buildGraph` / 整个 UI 都不知道数据来自硬盘还是打包产物。
示例一旦分叉出自己的流水线，它就会慢慢和真实路径失去同步，
变成一个「只有演示时才对」的假象。

### 踩到的两个坑

**1. 运行时 filter 删不掉产物里的 chunk。**
最初用 `import.meta.glob` 匹配全部根目录文件，再在运行时把 `package-lock.json` 过滤掉。
构建产物里照样躺着一个 91 KB 的 `package-lock-*.js`——`import.meta.glob` 在**打包时**
静态展开，运行时过滤只影响显示。必须写成 glob 的负模式 `'!/package-lock.json'`。
**看构建产物清单才发现的**，功能测试全绿。

**2. `import.meta.glob` 会排除调用它的模块自己。**
Vite 用这条规则避免自引用循环，于是示例里独独缺了 `demo.ts`，
而 `App.tsx` 和 `demo.test.ts` 都 import 它——两条边解析失败，示例的命中率不是 100%。
31 个文件的图上少两条边，肉眼绝对看不出来。
是端到端测试断言「真实失败 = 0」时炸出来的，
用 `'/src/adapters/demo.ts': () => import('./demo.ts?raw')` 手工补回。

### 附带产出：一个真端到端测试

`tests/demo.test.ts` 是全套测试里唯一喂**真实代码**的用例（其余都是手写小片段），
一路走完 scan → extract → resolve → graph，断言命中率 100%、
`main.tsx` 是入口点、影响范围的最远跳数 > 1。

它同时是示例的护栏：示例平时不执行，改坏了没人知道，
而它偏偏是部署后大多数人**唯一**会看到的那条路径。

## ADR-023：导出提取必须 lexer + 正则取并集 ★

**日期**：2026-09-03

**触发**：部署后拍截图，画面上 `src/core/types.ts` 的详情栏写着 `0 个导出`，
而侧栏同一时刻显示它的直接入度是 **10**。
**十个文件 import 一个没有任何导出的文件**——这个矛盾摆在同一屏上。

### 原因

`es-module-lexer` 报的是**运行时**导出。`export type` / `export interface` 编译后被完全擦除，
所以它一个都不报。**这符合 ES 规范，不是它的 bug**——我们用错了它的语义。

```
源码：export type FileNode = {...}   export const REAL = 1   export function fn() {}
lexer：["REAL", "fn"]                       ← 类型全丢
正则：["FileNode", "REAL", "fn"]            ← 全在
```

正则兜底本来就覆盖 `interface|type|enum`，但它**只在 lexer 抛异常时才跑**（ADR-001 的设计）。
lexer 处理纯类型模块时不抛异常——它成功了，只是返回空。于是兜底永远不会被触发。

### 修复

lexer 成功之后仍然跑一遍正则，**export 侧取并集**。
import 侧保持只信 lexer（它在那边是权威的，而且正则在 import 上更容易误判）。

### 影响面

| 仓库 | 修复前导出符号 | 修复后 | 漏报比例 |
|---|---|---|---|
| excalidraw | 2157 | 2495 | 13.5% |
| vite | 1871 | 2161 | 13.4% |
| tanstack/query | 1443 | 1767 | 18.3% |
| 本仓库 | 62 | 103 | 39.8% |

符号引用（symbolEdges）数量**一条没变**——import 侧的子句解析本来就处理 `import type`，
边一直是对的，缺的只是导出清单。所以从前的表现是：
边指向一个不在符号表里的名字，静默丢弃。

疑似死代码数量相应上升（本仓库 13 → 24），这是正确的：以前我们对类型导出完全失明。

### 为什么测试没抓到

`tests/extractor.test.ts` 里测导出的用例喂的都是**含运行时导出的混合模块**，
lexer 在那些用例上返回非空，断言就过了。没有一个用例是**纯类型模块**。
命中率、边数、符号引用数这些聚合指标全部正常——
唯一暴露它的是详情栏上那对自相矛盾的数字。

### 教训

**第三方库的返回值要问「它的语义是什么」，不是「它返回了什么」。**
`es-module-lexer` 的文档写得很清楚它遵循 ES 语义，
是我把「ES 模块的导出」当成了「TS 文件的导出」。
ADR-001 选它的理由（体积小、够用）依然成立，但「够用」的边界比我当时以为的窄一格。
