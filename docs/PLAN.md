# Code Atlas — 项目计划书

> 工作名，可改。

**一句话定义：把本地代码仓库解析成可交互的依赖关系图——左侧 IDE 式目录树，右侧力导向图，双向联动，全程在浏览器本地运行，代码不上传。**

---

## 1. 项目定位

### 解决什么问题

接手一个陌生代码库时，最难的不是读某个文件，而是搞清楚**文件之间怎么连的**：谁依赖谁、哪个文件是枢纽、哪块是孤岛、有没有循环依赖。目录树只能告诉你文件在哪，告诉不了你它们的关系。

### 目标用户

- 接手陌生项目的开发者
- 想在动手重构前先看清结构的人
- 想给别人讲清楚"我们项目长什么样"的人

### 与 CodeGraph 类工具的关系

CodeGraph（`colbymchenry` / `codegraph-ai`）这类工具把代码库索引成图，**通过 MCP 喂给 AI agent**——目的是让 agent 少读文件、省 token。

它们的原材料和本项目高度重叠（符号 + 依赖关系），但**消费者不同**：

| | CodeGraph 类 | Code Atlas |
|---|---|---|
| 消费者 | AI agent | **人眼** |
| 产出 | 可查询的索引库 | 可看、可点、可分享的图 |
| 门槛 | 装、配 MCP、跑索引 | 打开网页，选个目录 |

**立足点**：用 CodeGraph 时你只能通过问 AI 间接获取信息，永远看不到全貌。总有那么一刻你想的是「我就想直接看一眼这项目长什么样」——**那一刻它给不了你，这就是本项目存在的理由。**

（`codegraph-ai` 有 VS Code 扩展，但仍锁在 IDE 里，不是独立可分享的全景图。）

### 明确不做什么

边界写清楚，避免范围蔓延：

- ❌ 不做代码编辑（不是 IDE）
- ❌ 不做 AI 分析（零 API 成本是硬约束）
- ❌ 不做后端、不做账号、不做数据库
- ❌ 不追求 100% 解析准确率（追求「够用 + 诚实展示失败」）
- ❌ **不做调用图（L3）**——`a()` 调用 `b()` 这种关系需要类型推断，等于写一个类型检查器，见 ADR-003
- ✅ V1 做到**文件级（L1）+ 符号级（L2）**

### 为什么做这个（求职视角）

这个项目要能支撑住面试里的三类追问，所以每个技术决策都要留下理由：

1. **取舍类**：为什么不用 tree-sitter？为什么不做后端？
2. **难点类**：模块路径解析怎么做的？失败的怎么处理？
3. **性能类**：几千个文件怎么不卡？

> **纪律：每做一个技术决策，就往 `docs/DECISIONS.md` 追加一条。做完项目那份文档比代码值钱。**

## 2. 功能范围

### V1（两周内必须完成）

| # | 功能 | 说明 |
|---|---|---|
| 1 | 选择本地目录 | File System Access API，零上传 |
| 2 | 扫描文件树 | 支持 `.gitignore` 忽略规则 |
| 3 | 提取依赖 | JS/TS 用 `es-module-lexer`，其他语言用正则规则表 |
| 4 | 模块路径解析 | **核心模块，自研** |
| 5 | 左侧目录树 | 虚拟化，支持折叠/搜索 |
| 6 | 右侧力导向图 | 默认 2D，可一键切 3D |
| 7 | 双向联动 | 点树 → 图聚焦；点图 → 树定位展开 |
| 8 | hover 高亮 | 高亮该节点的上下游依赖 |
| 9 | 按文件夹着色 | 一眼看出模块边界 |
| 10 | 基础筛选 | 隐藏 `node_modules`、按扩展名过滤、按目录过滤 |
| 11 | **解析报告** | 命中率 + 失败清单。**诚实展示局限，这是加分项不是减分项** |
| 12 | **符号级钻取（L2）** | 展开文件节点 → 显示其导出符号；边细化到「用了哪个符号」 |
| 13 | **疑似死代码检测** | 无入边的导出符号 = 疑似未被使用。L2 的白送功能 |
| 14 | **循环依赖高亮** | 图上把环画出来。文字列表看不清环，这是可视化最有优势的场景 |
| 15 | **入口点导航** | 识别 `main.*`/`index.*`/package.json entry/无入边文件，作为「从这里开始看」的起点 |
| 16 | **影响范围高亮** | 点击节点 → 高亮其传递依赖（blast radius） |

> 功能 14–16 来自对 CodeGraph 工具清单的借鉴（见 ADR-004）。三者都只是在已有图数据上做文章，不引入新依赖、不引入新解析，合计约 1.5 天。
>
> **节点大小用「传递入度」而非代码行数**——被依赖得多的文件才是枢纽，LOC 大只说明文件长。

### V2（V1 上线且有人用之后再说）

- 增量重解析（借鉴 CodeGraph 的 `(size, mtime)` + 内容哈希 reconciliation，结果缓存到 IndexedDB）
- 圈复杂度编码为节点颜色
- 直接输入 GitHub URL 拉取仓库
- 导出 PNG / JSON
- 扩展更多语言

### 明确不做（非「以后再说」，是「不做」）

- **L3 调用图**：`a()` 调用 `b()` 的关系。理由见 ADR-003。

## 3. 技术架构

```
┌─────────────────────────────────────────────┐
│ UI 层 (React + TypeScript)                  │
│   ├─ 左：目录树      react-arborist          │
│   └─ 右：图渲染      react-force-graph       │
│           ↕ 共享 selection / hover 状态      │
├─────────────────────────────────────────────┤
│ 数据层                                       │
│   graphology  (图结构 + ForceAtlas2 布局)    │
├─────────────────────────────────────────────┤
│ Worker 层 (comlink 隔离，避免阻塞 UI)         │
│   ├─ 目录扫描    File System Access API      │
│   ├─ 依赖提取    es-module-lexer + 规则表     │
│   └─ 路径解析    自研 ★核心                   │
└─────────────────────────────────────────────┘
```

### 轮子清单

| 用途 | 库 | 选它的理由 |
|---|---|---|
| 读本地目录 | File System Access API | 浏览器原生，零上传，无需后端 |
| JS/TS 依赖提取 | `es-module-lexer` | 几 KB，只做 import/export 提取，不建完整 AST |
| 图数据结构 + 布局 | `graphology` | 自带 ForceAtlas2，数据与渲染解耦 |
| 图渲染 | `react-force-graph` | 同一份数据 2D/3D 一键切换 |
| 目录树 | `react-arborist` | 虚拟化，几千文件不卡 |
| Worker 通信 | `comlink` | 像调本地函数一样调 Worker |
| 构建 | Vite + React + TS | 产物可直接嵌进现有 Astro 个人站 |
| 测试 | Vitest | 解析器和路径解析是纯函数，天然可测 |

### 数据流

```
用户选目录
  → Worker: 递归扫描，产出 FileNode[]
  → Worker: 逐文件提取 import 原始字符串
  → Worker: 路径解析 → DepEdge[] + ResolveFailure[]
  → 主线程: 构建 graphology 图
  → 渲染: 目录树 + 力导向图
```

## 4. 数据模型

```ts
type FileNode = {
  id: string        // 相对仓库根的路径，唯一标识
  path: string
  name: string
  ext: string
  size: number      // 字节
  loc: number       // 行数，用于节点大小
  dir: string       // 所属目录，用于着色
}

type DepEdge = {
  source: string    // FileNode.id
  target: string    // FileNode.id
  raw: string       // 原始 import 字符串，便于调试
  kind: 'static' | 'dynamic' | 'type'
}

type ResolveFailure = {
  source: string
  raw: string
  reason: 'external' | 'unresolved' | 'ignored'
}

// ─── L2 符号级 ───

type ExportSymbol = {
  id: string        // "src/utils/index.ts#format"
  file: string      // FileNode.id
  name: string      // "format"
  kind: 'function' | 'class' | 'const' | 'type' | 'default' | 'reexport' | 'unknown'
  line: number
}

type SymbolEdge = {
  source: string      // 使用方 FileNode.id
  target: string      // ExportSymbol.id
  importedAs?: string // 别名：import { format as fmt }
}
```

`ResolveFailure` 不是错误日志，**它是产品的一部分**——解析报告直接展示它。

**死代码判定**：某个 `ExportSymbol` 没有任何 `SymbolEdge` 指向它 → 标记为**疑似**未使用。

> 必须用「疑似」而不是「未使用」——它可能被动态引用（`require(变量)`）、被外部包引用、或作为库的公开 API 被消费方引用。**界面上要写清楚这个不确定性，别把猜测说成结论。**

## 5. 核心难点：模块路径解析

### 为什么它是核心

提取 `import './utils'` 只要十行代码。把它解析成真实存在的 `src/utils/index.ts` 要几百行。

**这个模块的命中率直接决定项目成败**——如果一半的 import 都连不上，画出来的图就是废的。

### 解析策略（按顺序尝试）

1. **判定外部包**：不以 `.` 或 `/` 开头，且不匹配 tsconfig `paths` 别名 → 标记 `external`，V1 不画进图
2. **别名替换**：读取 `tsconfig.json` / `jsconfig.json` 的 `compilerOptions.paths`，做前缀替换，替换后回到步骤 3
3. **相对路径归一化**：基于当前文件目录求出绝对路径
4. **候选文件尝试**（按序命中即止）：
   ```
   X
   X.ts  X.tsx  X.js  X.jsx  X.mjs  X.cjs  X.json
   X/index.ts  X/index.tsx  X/index.js  X/index.jsx
   ```
5. **全部失败** → 记入 `ResolveFailure`，`reason: 'unresolved'`

### 其他语言的规则表

每种语言只需两样东西：**一条提取正则 + 一条路径映射规则**。

| 语言 | 提取 | 路径映射 |
|---|---|---|
| Python | `^\s*(?:from\s+(\S+)\s+)?import\s+(.+)` | 点号转斜杠，找 `.py` / `__init__.py` |
| Go | `import\s+\(([\s\S]*?)\)` \| `import\s+"(.+?)"` | module path 去掉 module 前缀 |
| Java | `^\s*import\s+([\w.]+);` | 点号转斜杠 + `.java` |
| Rust | `^\s*(?:pub\s+)?use\s+([\w:]+)` | `::` 转斜杠，找 `.rs` / `mod.rs` |

> 加一种语言 = 加一行表 + 一个映射函数 ≈ 半小时。这是刻意的设计，不是偷懒。

## 7. 第一步：风险验证（Day 1）

在写任何 UI 之前，先回答一个问题：**路径解析在真实项目上能命中多少？**

### 做法

写一个最小 Node 脚本（不是浏览器，先图快）：

1. 递归扫描一个真实项目的 `src/`
2. 用 `es-module-lexer` 提取所有 import
3. 跑一遍路径解析逻辑
4. 输出：

```
总 import 数:        1247
外部包 (跳过):        412
成功解析:            801
解析失败:             34
─────────────────────────
内部 import 命中率:  95.9%

失败样本 (前 10 条):
  src/a.ts  →  '@/legacy/foo'
  ...
```

### 测试对象

选 3 个风格不同的真实项目（例如：一个 Vite+TS 项目、一个带 monorepo 的、一个纯 JS 老项目）。

### go / no-go 判据

| 命中率 | 决策 |
|---|---|
| ≥ 90% | 按原计划推进 |
| 75–90% | 推进，但把「解析报告」提到 V1 前排，坦白展示局限 |
| < 75% | **缩范围**：V1 只支持 JS/TS，先把这一种做到 95%+ |

## 8. 验收标准（可量化）

- [ ] 在 3 个真实开源项目上，内部 import 解析命中率 **≥ 85%**
- [ ] L2：命名导入能正确对应到目标文件的导出符号，抽样准确率 **≥ 90%**
- [ ] L2：死代码列表**全部标注为「疑似」**，界面写明可能的误报原因

## 10. 决策记录（起始）

完整记录见 `docs/DECISIONS.md`。开工前已确定的三条：

**ADR-001：不用 tree-sitter，用 `es-module-lexer` + 正则规则表**
画依赖图只需要 import 语句，不需要完整 AST。tree-sitter 每种语言要加载一个 WASM 语法包并写一遍 query，加语言的成本是「几天」；规则表方案是「半小时」。准确率的损失换来了两个数量级的扩展成本下降，对这个用途是划算的。函数级钻取（V2）时再引入 tree-sitter。

**ADR-002：纯浏览器本地，无后端、无账号**
代码是敏感资产，不上传是硬需求而非营销话术——DevTools Network 面板可以自证。同时零服务器成本、零运维、零合规负担。代价是无法做跨设备同步和分享，V1 接受。

**ADR-003：做到符号级（L2），不做调用图（L3）**
「函数级」有三个层次：L1 文件级、L2 符号级（谁用了谁的哪个导出）、L3 调用图（`a()` 调用 `b()`）。L2 只需解析 import/export 名称，`es-module-lexer` 本来就同时返回两者，几乎零新增依赖，成本 +3~4 天，且白送一个「疑似死代码检测」功能。L3 需要知道 `obj.method()` 里 `obj` 的类型，等于写一个类型检查器（参考 Sourcegraph SCIP、GitHub stack-graphs 的工程量），**明确不做**。
